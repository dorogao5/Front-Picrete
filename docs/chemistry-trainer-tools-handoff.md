# Обвязка химического тренажёра: отчёт для повторного подключения

Дата: 12 сентября 2026. Назначение: перенести проверенные технические решения на другую дисциплину, не перенося вместе с ними предметные предположения и промежуточные ошибки. Отчёт объединяет результаты интеграции `essential_skills`, проверки банка, реальных запросов и выпуска. Хронологические записи в Studio содержат отменённые эксперименты; актуальные решения описаны здесь.

## 1. Главное и граница готовности

Работает связка: модель-генератор → один независимый верификатор, исправляющий ту же задачу → сохранённый полный эталон → помощник и проверка решения студента. Calculator, SymPy и справочник — инструменты этих моделей, а не дополнительные оценщики. Дополнительный классификатор задач для физхимии не нужен и не добавлен в этот путь.

Инструменты подключены к четырём ролям физхимии. В остальных дисциплинах флаги инструментов и выбранные модели сохранены. Это не глобальное переключение на Yandex.

**Не считать интеграцию доказанно безошибочной или готовой к массовому переносу без приёмки.** Последний обычный пакет из пяти дал три готовые задачи. Две попытки завершились по длине ответа, а не были ошибочно отклонены верификатором. После этого исправлены передача reasoning и контракт полного проверенного эталона; полный живой прогон 5/5 на окончательной версии ещё не подтверждён. Успех HTTP и прохождение JSON-схемы не доказывают химическую корректность или полноту решения.

Кодовая база, на которую опирается отчёт:

| Компонент | Проверенная ревизия до этой документирующей UI-правки |
| --- | --- |
| Rust API и worker | `209181790133a647052420a093608614345d1b2f` |
| Studio API/UI и образ шлюза | `b57bbb381ef6ab06ea88e1adcadf0edf4681a549` |
| Front | `c6576dd9d171d624db9c2e84f78d59cee4fc076b` |

Ревизия Front с этим отчётом определяется Git-коммитом файла и опубликованным `build-info.json`; остальные компоненты не требуют перевыпуска ради изменения подсказки.

## 2. Что переиспользуется, а что задаётся заново

Переиспользуются: приватный вычислительный шлюз, JSON definitions, безопасное выполнение инструментов, цикл function calling, учёт usage/ошибок, сохранение эталона и аудита исправлений, механизм передачи скрытого эталона помощнику, Git-процесс выпуска.

Для каждой дисциплины заново нужны:

- нотация и определения из фактических материалов курса;
- перечень подтем, уровни сложности и вручную проверенные задачи;
- несколько блюпринтов с допустимыми исходными данными, допущениями и полным образцом решения;
- проверенные few-shot примеры, включая типичные ошибки студента и корректную частичную работу;
- четыре редактируемых промпта: генератор, верификатор, помощник, оценивание;
- выбранные провайдеры/модели по ролям и отдельные разрешения инструментов;
- приёмочные сценарии для реального курса, а не только арифметические smoke-тесты.

**Важная граница:** существующая маршрутизация содержит предметный путь физхимии. Включение четырёх tools-флагов для неорганики само по себе не переводит её на весь этот путь, включая контракт `verified_task` и правила проверки. При переносе нужно явно проверить маршрутизацию и сделать необходимую политику курса настраиваемой. Не переименовывать неорганику в физхимию и не копировать условие по ID как универсальное решение.

Модель, разрешение инструментов, allowlist доступа и политика проверки — разные настройки. Изменение одной не должно скрыто менять остальные.

## 3. Контракт генерации и проверки

1. Сервер передаёт выбранную подтему/сложность, блюпринт, нотацию и образец. Модель меняет вводные в допустимой модели задачи. Подтема наследуется от запроса сервера: её альтернативное название от модели не должно создавать новую подтему или отбрасывать верную задачу.
2. Генератор возвращает полное условие, решение, ответ и критерии. Вычислительные инструменты используются для расчёта, а не для декоративного подтверждения.
3. Независимый верификатор проверяет числа, единицы, допущения, вывод и объяснения. При ошибке исправляет **эту же** задачу, сохраняя корректные исходные данные и замысел. Не генерирует замену только из-за расхождения решений.
4. В tools-пути физхимии успешная проверка обязательно возвращает полный `verified_task`: условие, reference solution, ответ, рубрику, баллы, сложность, подтему и предусмотренные контрактом данные/факты/изображения. Невозможность безопасно проверить или исправить означает неуспех, а не молчаливый допуск.
5. `verification.solution` и `verification.answer` — диагностические поля. Их нельзя автоматически накладывать на исходное решение как исправление: короткий комментарий верификатора может уничтожить полный эталон.
6. При исправлении сохраняется оригинал в `validation.correction.before`, а не только его хеш. Административный аудит не отдаётся студенту вместе с банком.
7. Структурная валидность полного объекта не заменяет предметную проверку. В частности, наличие строки solution не доказывает, что разобраны все пункты.

Именно подмена полного эталона коротким диагностическим решением была обнаружена в реальной задаче столкновений: HTTP 201 скрывал отсутствие двух пунктов разбора. Задача исправлена вручную с сохранением ID, без новой генерации. Контракт исправлен и покрыт тестами.

Техническая JSON-инструкция добавляется платформой после редактируемого промпта: выпуск нового контракта не должен зависеть от того, успел ли администратор обновить старое поле промпта. Старый tools-off путь `corrected_task` сохранён для совместимости; при переносе его нельзя считать идентичным новому.

## 4. Инструменты: реальные возможности и ограничения

| Инструмент | Для чего применять | Чего нельзя предполагать |
| --- | --- | --- |
| Calculator v3 | Численные выражения, логарифмы, экспоненты, корни, степени; Decimal, 34 значащие цифры | Не выводит размерности; `unit:null` означает отсутствие вывода единиц, а не безразмерность |
| SymPy v2 | Символьные преобразования, производные, уравнения с явно объявленными символами | Неудачное упрощение не доказывает ошибочность ответа; нужны область определения и допущения |
| reference_db | Одна запись со значением, единицами, условиями и источником | Таблица из 80 записей не является полностью независимо аттестованной базой; читать предупреждения |

Calculator получает численные выражения, а не символическую физическую формулу. Символ `pi` в нём не поддерживается: передавать численное значение, например `3.141592653589793`, сохраняя π в учебной записи. Для экспоненты использовать `exp(...)`. Литералы разбираются непосредственно в Decimal, без промежуточного float. Численный результат находится в `normalized_result.value` и передаётся строкой; SymPy возвращает `normalized_result.result`, справочник — `normalized_result.record`.

Молярные/молекулярные величины, перевод единиц, стехиометрия и область применимости формулы остаются обязанностью модели и автора блюпринта. Калькулятор может безошибочно посчитать химически неверную формулу.

У справочника сохранены исходные значения и точность, введены `review_warnings`. В частности, отмечена проблема исходной маркировки брома как моноизотопного. Для нового курса сначала вручную проверить реально используемые записи; не отправлять модели всю таблицу.

Ошибочный аргумент инструмента разрешается исправить в том же диалоге. Технический сбой не превращается в «студент ошибся». Нельзя выдумывать результат, бесконечно повторять одинаковый ресурсный сбой или считать текст tool result инструкцией для модели.

## 5. Function calling, reasoning и параметры моделей

Используется native function calling: модель возвращает запрос инструмента, приложение выполняет его через приватный HTTP `POST /invoke` и возвращает результат в тот же диалог. Публичный MCP-сервер и открытый Yandex доступ к шлюзу для этой схемы не требуются.

**Сохранять `reasoning_content` текущей цепочки вызовов Qwen и DeepSeek.** Промежуточный эксперимент с удалением reasoning Qwen дал смешанные результаты в микротестах и не решил реальные длинные задачи; это не рекомендация для переноса. Финальная реализация сохраняет reasoning в оперативном контексте, не в ответе студенту и не в аудите.

Основание для семантики — [официальный шаблон Qwen](https://huggingface.co/Qwen/Qwen3.6-35B-A3B/blob/main/chat_template.jinja): reasoning после последнего пользовательского сообщения относится к текущему ходу. Параметр сохранения более старых ходов — другая задача. Совместимость конкретного хостинга всё равно проверяется реальным запросом.

Если после успешного инструмента модель вернула пустой final, допускается **одно** завершение того же контекста с `tool_choice=none`, без новых вычислений и новой задачи. Инструкция добавляется к существующему system, а не новым user-сообщением, которое меняет границу текущего хода. Повторная пустота, отказ, HTTP-ошибка или пустота до успешных инструментов не запускают регенерацию. Продолжение учитывается в usage и общем deadline.

Генератор и верификатор: первый `tool_choice=required`, дальше `auto`. Помощник и оценивание: `auto`; вопрос «с чего начать» не требует искусственного вычисления. По умолчанию 8 раундов / 24 вызова инструментов, конфигурируемые пределы до 32 / 96. Это защита цикла, а не предметный фильтр задач. Общие deadline: Studio 300 с, Rust 110 с. Любое увеличение требует согласованной проверки upstream/proxy, а не только одного таймера.

Точные URI моделей имеют операторские настройки, отдельно от выбора модели для курса:

```json
{
  "LLM_MAX_OUTPUT_TOKENS_BY_MODEL": {
    "gpt://<folder>/<selected-qwen-model>": 81920
  },
  "LLM_SAMPLING_BY_MODEL": {
    "gpt://<folder>/<selected-qwen-model>": {
      "temperature": 0.6,
      "top_p": 0.95,
      "presence_penalty": 0.0
    }
  }
}
```

Это наглядное представление двух env-переменных; каждая в окружении содержит собственную JSON-карту. В проде переопределение задано только для выбранного Qwen; другие модели остаются без изменений. Явный `max_tokens` конкретного запроса имеет приоритет. Отсутствующие sampling-поля не меняются. Невалидные значения/дубликаты/неизвестные поля отклоняются безопасно, без вывода секретов.

81920 — резерв, а не целевой расход. Отсутствие лимита в payload не означает отсутствие лимита у провайдера. Одно увеличение резерва проблему не решило: была попытка с 81920 output tokens и всё равно `finish_reason=length`. Настройки .6/.95/0 — исходная точка для точных задач, не доказательство устранения всех ошибок и не универсальный оптимум. Источники для повторной сверки: [карточка Qwen](https://huggingface.co/Qwen/Qwen3.6-35B-A3B/blob/main/README.md), [модели Yandex AI Studio](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/models), [Chat Completions API](https://aistudio.yandex.ru/en/docs/ai-studio/api/Chat-Completions/createChatCompletion).

При Compose использовать `${VAR:-}`, не `${VAR:-{}}`: вложенные фигурные скобки уже приводили к повреждению JSON. Пустая строка означает пустую карту. Проверять окружение API, worker и Studio внутри реально запущенных контейнеров, не только файл на диске.

В Rust размер модельного HTTP-ответа допускается до 4 MiB: прежний предел 256 KiB конфликтовал с большим reasoning. Это не описание лимита streaming-адаптера Studio. Шлюз ограничивает собственный результат 128 KiB; Studio дополнительно проверяет полученный gateway response на 256 KiB. Строгая JSON-схема сохранена; гипотеза «схема несовместима с tools» не была подтверждена и не должна стать правилом переноса.

## 6. Приватность и эксплуатация шлюза

Исходный пользовательский `essential_skills` не изменён. Адаптированная версия находится в Studio `essential_skills/`; определения инструментов согласованы между Studio, Rust и шлюзом.

Шлюз работает в приватной Docker-сети без публичных портов и исходящего доступа, от непривилегированного пользователя, с read-only FS, снятыми capabilities, `no-new-privileges`, лимитами памяти/процессов/CPU. До четырёх вычислительных workers; для отдельного вычисления ограничены ресурсы и время. Это ограничения исполнения недоверенного выражения, не маленький лимит reasoning модели.

SymPy использует разрешённый AST и объявленные символы; не добавлять произвольный Python/eval ради удобства. Доступ приложения к gateway аутентифицирован. Исходный CSV монтируется read-only из приватного файла; не помещать его, API-ключи, cookies или reasoning в публичные репозитории, образы, CI-логи и ответы студенту.

Ранее схема с loopback-портом не работала в фактической internal-сети. Рабочая схема — приватный адрес gateway в общей сети. При переносе проверить связность именно из API/worker/Studio, а не только с хоста. Адрес сети — настройка окружения, не константа курса.

## 7. Предметные выводы из физхимии

Локально просмотрены 20 типовых примеров и 11 PDF / 343 страницы лекционного каталога. **Лекций по кинетике в этом каталоге нет**: общая нотация взята из имеющихся лекций, кинетические модели — из примеров и Ерёмина. Нельзя заявлять полное совпадение с отсутствующей лекцией. Файлы лекций в материалы сервиса не загружались; перенесены извлечённые правила и обозначения.

Подготовлены пять подтем, 15 сочетаний «подтема × уровень», 10 few-shot примеров, шесть справочных листов и четыре промпта. Статический банк — 64 задачи, включая 23 запрошенных номера Ерёмина:

| Подтема | Базовые | Средние | Сложные | Всего |
| --- | ---: | ---: | ---: | ---: |
| Формальная кинетика | 8 | 0 | 0 | 8 |
| Аррениус | 7 | 12 | 0 | 19 |
| Михаэлис–Ментен | 5 | 18 | 0 | 23 |
| Последовательные реакции | 6 | 3 | 0 | 9 |
| Теория столкновений | 3 | 1 | 1 | 5 |

Наличие уровня в интерфейсе не означает наличие готовых задач этого уровня. Пустой банк нужно объяснять честно. Сложность определяется действиями и допущениями, а не количеством подпунктов или словом «сложные» в названии раздела.

Ошибки, которые важно перенести в предметные инструкции, а не в набор хрупких строковых фильтров:

- Порядок реакции нельзя выводить из стехиометрии без основания. Согласовать определение скорости и единицы k.
- Аррениус: температуры в K, знак разности обратных температур, согласованные единицы R/E. Для мономолекулярного разложения нельзя без оговорок объяснять предэкспоненту простой бимолекулярной частотой столкновений.
- Столкновения: `r=k[A][B]`, а не `r=A_exp[A][B]`; в модели `k=P A_coll(T) exp(-E0/RT)`. Не смешивать молекулярную приведённую массу с R или молярную с k_B. Проверять N_A, перевод м³ в литры, диаметр/сечение и множитель 1/2 для разных/одинаковых частиц. При предэкспоненте, пропорциональной √T, различать E_a и E0.
- Последовательные реакции: начальные условия, баланс, условие максимума промежуточного продукта, отдельный предел равных констант.
- Михаэлис–Ментен: `[S]≫[E]` не означает `[S]≫K_M`; при `[S]=K_M` скорость равна половине максимальной. Конкурентное ингибирование меняет кажущийся K_M, но не максимальную скорость.
- Округление допустимо, неверные промежуточные равенства — нет. Не заменять исходные числа «задуманными круглыми» значениями.
- Few-shot нужно проверять не менее тщательно, чем банк: он тиражирует как правильную структуру, так и ошибку.

## 8. Работа со студентом и интерфейс

Эталон передаётся сервером помощнику/проверяющему, но не раскрывается автоматически студенту. В обычном диалоге помощник определяет текущий шаг, даёт небольшую подсказку и вопрос. Полный разбор — отдельное явное действие, а не стандартный ответ на «с чего начать». Инструментальные вычисления не дают права раскрывать будущие числа.

Оценивание учитывает корректные промежуточные шаги и альтернативный метод. Одну исходную ошибку не следует повторно штрафовать за каждый последующий перенос. Неполное читаемое решение не является нечитаемым; технический сбой не является нулевой оценкой.

Генерация открывается после трёх **разных решённых задач канонического банка этой подтемы**, независимо от уровня. Черновики, создание попытки, просмотр подсказки/эталона и сгенерированные задачи не подменяют этот счётчик. Проверка серверная: скрытие/disabled кнопки недостаточно.

Причина блокировки должна быть видна без hover и доступна с клавиатуры. Формулировка: «Решите 3 разные задачи из банка этой подтемы чтобы генерировать новые задачи.» Дополнение: «Подойдёт любой уровень сложности.»

Обычный запрос — пять задач. Защита от двойного клика и состояние ожидания обязательны. При результате 3/5 показывать «Набор сформирован частично: готово 3 из 5 задач. Можно решать готовые задачи», а не «ожидают проверки», если фоновой работы уже нет. Не запускать скрытое пополнение пакета за дополнительные токены.

## 10. Как подключать общую и неорганическую химию

1. Зафиксировать текущие модели, флаги, активный снимок, банк и ревизии; не менять другие курсы.
2. Уточнить предметный путь проверки. Отдельно выбрать политику «генератор + один независимый verifier с ремонтом той же задачи», если она нужна этому курсу. Не предполагать, что tools-флаги уже переключили маршрутизацию.
3. Из материалов курса извлечь обозначения, конвенции и ограничения. Возможные темы для разработки, а не уже реализованный банк: стехиометрия, растворы, кислотно-основные равновесия, ОВР, комплексообразование, осаждение.
4. Для каждого выбранного блюпринта вручную определить химически допустимые вводные: материальный и зарядовый баланс, фазы/растворимость, степень диссоциации, условия применимости приближений, активности или концентрации, температуру констант. Не навязывать одну физхимическую систему обозначений другому курсу.
5. Проверить нужные записи справочника. Арифметику поручать calculator, алгебру SymPy; дополнительные справочные данные добавлять с источниками и условиями, не по памяти модели.
6. Подготовить небольшой проверенный банк и few-shot для каждого уровня. Разделить условие, скрытый полный эталон, критерии, пошаговые подсказки и явный полный разбор.
7. Выбрать модели по ролям в Studio. Параметры точного URI и разрешения tools включать адресно. Сначала dry-run конфигурации и тесты без платных вызовов.
8. Выпустить через Git; только затем ограниченные реальные проверки с заранее заданным бюджетом и сценариями. Исправлять сохранённые задачи, не перегенерировать банк ради тестирования.
9. Проверить генерацию обычного пакета, решение/оценивание/помощь, блокировку 2→3 и независимость подтем/курсов. Проверить сбой gateway, пустой final, длину, частичный пакет и отсутствие двойной генерации.
10. Включать для студентов после ручной проверки результатов и фиксации оставшихся ограничений. Не обещать «идеально» по единичному удачному ответу.

## 11. Карта исходников и выпуск

Репозитории лежат рядом: `Front-Picrete`, `Studio-Picrete`, `Picrete` (Rust).

- Studio: `essential_skills/`; `backend/app/llm/essential_tools.py`; `backend/app/services/taskgen.py`; предметные сервисы/контракты; `ops/content/physical_chemistry/` (profile, blueprints, sheets, prompts, reviewed-bank, eryomin-bank, аудиты).
- Rust: `src/services/essential_tools.rs`, `ai_grading.rs`, `assistant_chat.rs`, `essential_tools_instruction.txt` и JSON definitions.
- Front: `src/pages/CourseTrainer.tsx`, `CourseTrainer.test.mjs`.
- Исходный пакет пользователя: каталог `qwen3.5-2B-Chem/essential_skills`; не считать его автоматически идентичным усиленной серверной адаптации.

Для шлюза нужен интерпретатор с SymPy; backend-venv намеренно не содержит SymPy. Не собирать gateway-тесты этим venv. CI также требует тестовую зависимость jsonschema; приватная таблица не должна попадать в CI ради устранения намеренного skip.

Процесс: локальные адресные изменения → тесты → коммит/push → CI → серверный fetch именно SHA → сборка/выпуск → readback версии и данных. Не копировать исходники с ноутбука в работающий контейнер. Проверять SHA API и worker, OCI revision Studio, публичные build-info UI; одного локального `git status` недостаточно.

Контент публикуется отдельно через штатный release-путь: dry-run, проверка digest, применение, readback активного снимка. Совпадение SHA кода не доказывает совпадение промптов и банка. Обновление задачи проходит штатное редактирование, снимает старое подтверждение и требует повторного допуска. ID сохраняется; номер экспорта вычисляется из группировки/порядка, поэтому его стабильность проверяется отдельно. При правке только topic подтверждение сбрасывается, но content fingerprint может остаться прежним: topic в него не входит. `correction.before` хранит снимок перед исправлением верификатора, а не универсальную историю всех ручных правок.

Приёмка переноса закончена только когда есть доказательства всех четырёх вещей: правильный код в проде, правильная конфигурация курса, правильный опубликованный контент и рабочий пользовательский сценарий. На сегодня следующий существенный незакрытый пункт физхимии — полный живой пакет на финальной версии и ручная проверка всех его условий/эталонов, а не очередная перестройка инфраструктуры.
